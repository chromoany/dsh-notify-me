# Compatibility

Per-release adaptation records live in [package.json](../package.json) under `dsh.compatibility.dshReleases`; hosts from `0.2.1-rc.2` on gate installation on `peerDependencies` and `engines` only and no longer read that field, so it is a human-readable record, not a gate.

Every release was tested to **actually activate**: `0.1.1-rc.2`, `0.1.2-rc.1`, `0.1.5-rc.1`, `0.1.5-rc.2`, `0.2.0-rc.2`, `0.2.1-rc.2`, `0.2.1-rc.3`, `0.2.1-rc.4`, `0.2.1-rc.5`, `0.2.2-alpha.2`, `0.2.2-rc.1` and `0.2.2-rc.2` (the criteria: the plugin entry lands in the boot page's `__DSH_BOOT__`, its inject dependencies resolve, `/plugins/??dsh-notify-me/client.js&rev=…` serves a build containing the new code, and the "Notify me" section appears in Settings). Plugin entries stay compatible from `0.1.1-rc.2` through `0.2.2-rc.2`, and stepping back to an older host needs no config change; the `1.9.0` settings redesign added no new host API, and the bell in the settings page header is the plugin's own SVG (`docs/brand/`).

<summary>Host-generation shape differences and two known traps</summary>

The plugin picks its interaction source per host generation; the table below marks the boundaries of each shape, not a gate:

| Host generation | "Needs you" interaction source | Current session | Toast-click navigation |
| --- | --- | --- | --- |
| `<= 0.1.2-alpha.1` | controller snapshot `pending[]` | snapshot `current` | `sessions.open()` |
| `0.1.2-alpha.2 .. 0.1.6-alpha.1` | `uiSession.pendingInteractions` | snapshot `current` | `sessions.open()` |
| `>= 0.1.6-alpha.2` (incl. `0.2.0-rc.2`, `0.2.1-rc.2`, `0.2.1-rc.5`, `0.2.2-alpha.2`, `0.2.2-rc.1`, `0.2.2-rc.2`) | `uiSession.sessionStatus` | `retainedBy.mainView` | `uiWorkspace.openSession()` |

The ranges are illustrative: the plugin picks its source by store shape (whenever `sessionStatus` exists it takes the new path), and the version numbers only mark where each shape appeared. The `peerDependencies` range shapes npm's peer warning — `0.2.1-rc.2`, `0.2.2-alpha.2`, `0.2.2-rc.1` and `0.2.2-rc.2` all fall inside `>=0.2.0-rc.1 <0.3.0-0`, so no exemption is needed.

The isolated run on `0.2.2-rc.2` (2026-11-13): 76 boot entries (1 bootstrap plus 57 and 18 in `application` batches), the `dsh-notify-me` entry in the second `application` batch with all three inject targets (`client-ui-session`, `client-locale`, `client-ui-conversation`) present; `/plugins/??dsh-notify-me/client.js&rev=…` served 275,450 B — the repository's 1.20.1 `lib/client.js` (275,380 B) plus the host's 70 B sourceMappingURL comment — HTTP 200; loaded into a real page through headless Edge over CDP, `apply` ran normally and `debug()` reported `version: 1.20.1` and `uiSession: bound` (it starts `unbound` right after page load and flips to `bound` once a session is open, still the lazy timing), opening Settings from the account menu and clicking "Notify me" rendered the whole view with "plugin version: dsh-notify-me v1.20.1" in the footer and host version `0.2.2-rc.2` in General settings. The host client bundles still differ from `0.2.2-rc.1`, but the store shapes this plugin relies on (`uiSession.sessionStatus`, `retainedBy.mainView`, `uiWorkspace.openSession()`) and the three inject targets are unchanged.

`0.2.1-rc.3`, `0.2.1-rc.4`, `0.2.1-rc.5`, `0.2.2-alpha.2` and `0.2.2-rc.1` each got an isolated run: an isolated `DSH_HOME` with the plugin installed, then `dsh web --no-open` (71 boot entries on `rc.3` / `rc.4` / `rc.5`, 72 on `0.2.2-alpha.2`, 74 on `0.2.2-rc.1`), the `dsh-notify-me` entry in the `application` batch (`0.2.2-rc.1` turns the boot payload into entries + batches loaded batch by batch; the plugin entry itself is unchanged), and all three inject targets (`client-ui-session`, `client-locale`, `client-ui-conversation`) present; `/plugins/??dsh-notify-me/client.js` served the build of the day (`rc.3` / `rc.4` the 1.16.1 build at 248,023 B, `rc.5` the 1.17.0 build at 252,562 B; `0.2.2-rc.1` served the repository's 1.17.0 `lib/client.js` itself, with only the host's 70 B sourceMappingURL comment appended — HTTP 200); loaded into a real page through headless Edge over CDP, `apply` ran normally and `debug()` reported `uiSession: bound`, `uiSessionSource: sessionStatus`, `raiseChannel: window-focus` (on `0.2.2-rc.1` we also checked `version: 1.17.0` and `notifyTagLimit: 64`; right after page load with no session open `uiSession` is `unbound`, and it flips to `bound` about 1.5 s after a new session is opened, which is the plugin's normal lazy service-lookup timing), opening Settings from the account menu and clicking "Notify me" rendered the whole settings view (on `0.2.2-rc.1` it also showed "plugin version: dsh-notify-me v1.17.0", with the host version `0.2.2-rc.1` in General settings), and the web host logged no warnings or errors (the single 404 was the optional desktop Electron page-bridge probe `/__dsh-notify-me/host-bridge`, which the plugin records as `hostBridge.state: unavailable` and which does not affect alerts). All four older releases ship host client bundles that differ from `0.2.1-rc.2` (`dsh-client-ui-workspace`, `dsh-client-ui-conversation`, `dsh-client-locale`, …), yet every one of the four session-row slots the plugin uses, plus `uiSession.sessionStatus`, `retainedBy.mainView` and `uiWorkspace.openSession()`, is still there; `0.2.2-alpha.2` adds a `sidebar.session.row.trailing` slot the plugin does not use; `0.2.2-rc.1` again changes the client bundles of `dsh-client-ui-session`, `dsh-client-ui-workspace`, `dsh-client-ui-conversation`, `dsh-client-locale`, `dsh-client-modules` and `dsh-client-ui-approval`, and all the surfaces the plugin uses are still there. The `0.2.1-rc.5` desktop shell `lib/main.js` still forwards generically (no per-route allowlist), so the plugin's exact Windows raise route is unaffected; the `0.2.2-rc.1` shell also forwards generically and still does not register a Service Worker, and we probed that route on the installed desktop (Windows): GET 200, bad `Host` / cross-origin / wrong method 403 / 403 / 405, and POST really raised the window. Host-side shapes still match `0.2.0-rc.2`; no code change was needed.

Two traps are worth remembering: a package listed in `dsh.client.inject` that a newer runtime no longer ships parks the client entry at `pending (waiting for services: …)` forever — which is exactly how 1.1.3 broke on `0.1.2-rc.1` and later; and when the host swaps a store or a field name nothing throws, alerts just go **silent** — `pendingInteractions`→`sessionStatus`, `list.current`→`retainedBy.mainView` and `sessions.open()`→`uiWorkspace.openSession()` were all this kind. So every adaptation has to confirm with `window.__dshNotifyMe.debug()` that it really reports `bound`.
